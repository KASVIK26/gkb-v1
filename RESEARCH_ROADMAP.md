## 0. TL;DR

1. **The biggest problem is data integrity, not code or Neo4j.** Almost all the "knowledge" in the repo was generated by an LLM and never checked:
   - **31 of 48 downloaded "curated" papers (65%) have nothing to do with crops.** The PMIDs in `scripts/fetch_papers.py` point to papers on sports medicine, diabetes, brain injury, psychiatry, and so on. The titles and notes in that list were made up.
   - **All 4 records in `data/review_queue.json` are hallucinated.** The "Sr/Lr/Yr → HD2781, HD3086…" records came from a *neural stem cell* paper (PMID 37228583). The LLM read the made-up `TITLE:`/`NOTE:` header that the fetcher wrote above the paper, not the paper itself.
   - **The 22 seed edges contain many factual errors.** Examples: wrong chromosomes (Sr35 on "9B", but wheat has no chromosome 9), genes placed in the wrong crop (Cre8 is a *wheat* nematode gene), gene names that don't exist (Scn3, Rst, Ml26), made-up chickpea gene IDs, and Chinese Spring shown as carrying genes it does not have. The confidence labels were invented.
2. **The project doesn't yet model its actual goal.** The goal is *variety → susceptibility → environmental trigger → IoT flag*. The schema has no susceptibility relation, no environment/trigger entity, no pathotype/race, no growth stage, no location/zone, and no evidence/provenance entity.
3. **The genome datasets are good choices but are used badly.** The pipeline parses 136k wheat genes just to count them, and throws away the functional annotation. That annotation can identify about 1,700 wheat, 374 soybean and 121 chickpea NLR resistance-gene candidates, and can anchor QTL intervals to real genes.
4. **Losing the graph when Aura Free deleted the idle instance was a design flaw.** The graph should be a *build artifact*, rebuilt from versioned source files in minutes. It should never be the only copy of the knowledge.
5. **The fix is a "verification-first" pipeline:** verified sources → structured parsing → schema-constrained, evidence-grounded LLM extraction → ontology normalization → claim + evidence store → computed confidence → graph → APIs for the IoT and phenomic/yield modules. It must be measured against a hand-annotated gold standard. That measurement is what makes it research-grade and publishable.

## 1. What this module must deliver (reframed objective)

The Genomic KB is the **prior-knowledge layer** of the AgriHub system. The other two modules observe the field (IoT sensors, phenomic images). This module answers: *given this variety, in this place, at this growth stage, under these weather conditions, which diseases are plausible, how strongly, and why (with citations)?*

### 1.1 Primary outputs

| # | Output | Consumer |
|---|---|---|
| O1 | **Variety × Disease reaction matrix** (R / MR / MS / S, with stage, pathotype, location, evidence tier) for varieties notified in India | IoT risk engine, UI, yield model |
| O2 | **Disease environmental-trigger library**: machine-readable envelopes (temperature, RH, leaf wetness, soil moisture/temperature, rainfall, duration, growth-stage window), each with citations | IoT device firmware/cloud rules |
| O3 | **Gene/QTL → disease knowledge** with effectiveness against pathotypes over time and region ("which deployed genes are still effective in zone Z") | Breeders, UI, risk engine |
| O4 | **Risk API**: `(crop, variety, zone, growth_stage, sensor_window) → ranked disease risk flags + explanation + evidence` | IoT module |
| O5 | **Feature/prior API**: per-variety resistance vector and disease priors | Phenomic model (Bayesian re-weighting of classifier output), yield model (loss modifiers) |
| O6 | **Analytical findings**: variety vulnerability index, genetic-vulnerability (gene deployment) analysis, QTL → candidate-gene prioritization, knowledge-gap report | Research paper(s) |

### 1.2 Competency questions (CQs): the definition of "done"

A research-grade KG is specified by the questions it must answer. Every schema element must serve at least one CQ. Every CQ gets a Cypher query and a test.

| CQ | Question |
|---|---|
| CQ1 | Which notified varieties of crop C recommended for zone Z are **susceptible** (S/MS) to disease D, and on what evidence? |
| CQ2 | Given sensor readings over the last N hours and the growth stage in a field sown with variety V, which diseases have **favourable conditions AND V is not resistant**? (IoT flag) |
| CQ3 | Which resistance genes does V carry, **how was that determined** (marker, pedigree, gene postulation, sequencing), and are they still effective against pathotypes found in zone Z in the last K years? |
| CQ4 | Which genes have been **defeated** by which pathotypes, and when and where was this first reported? |
| CQ5 | Which QTLs are associated with disease D, where do they map on the reference genome, and which annotated genes (especially NLRs) lie inside their interval? |
| CQ6 | Which diagnostic markers can confirm gene G in a breeding line? |
| CQ7 | What environmental envelope favours disease D at each growth stage, with citations? |
| CQ8 | Which varieties or germplasm are **multi-disease resistance donors**? |
| CQ9 | How genetically vulnerable is zone Z? (share of popular varieties that rely on the same R gene) |
| CQ10 | Where is evidence **conflicting** (the same variety-disease pair reported as R in one study and S in another)? |
| CQ11 | Which popular varieties **lack reaction data** for the major diseases of their zone? (gap report) |
| CQ12 | For a phenomic-model prediction "disease D on variety V", what is the prior plausibility given variety, zone, stage and recent weather? |

### 2.2 Data-source and data-integrity problems (Critical)

#### D1. The paper corpus is mostly irrelevant (hallucinated PMIDs)

A keyword check of each file's body (crop name count, disease-term count, journal name) found:

| Crop folder | Files | Actually relevant | Irrelevant (examples of the real journal) |
|---|---|---|---|
| wheat | 20 | 9 | 11: Br J Sports Med, Diab Vasc Dis Res, J Psychiatr Res, Heart Fail Rev, Mol Med Rep, BMC Health Serv Res, Asian Pac Isl Nurs J, Front Mol Biosci (neural stem cells), Medicine, Sci Adv… |
| soybean | 13 | 1 (35096378, SCN review) + 1 wheat paper misfiled (37225584 is wheat powdery mildew, Egypt) | 11: Brain Inj, JGH Open, Neural Regen Res, Front Immunol, Foods, Antioxidants, Cureus, InFo Neurologie… |
| chickpea | 15 | 6 (34326558, 36825068, 37078928, 38390527, 38465028, 39952025) | 9: Front Psychol, Front Chem, PLoS One (non-crop), Sci Prog, Nat Commun (non-crop), J Comput High Educ… |
| **Total** | **48** | **16 (33%)** | **31 (65%)**, plus 1 misfiled |

Even the relevant files carry a **made-up `TITLE:`/`NOTE:` header**. For example, 38988305 is a real *Theor Appl Genet* wheat paper, but not the "Genome-wide atlas of rust resistance loci" the header claims. The header text is sent to the LLM along with the body, so the LLM "extracts" facts from the made-up note.

**Root cause:** the `CURATED_PAPERS` list was generated by an LLM. Nothing checked that a PMID's real title matches the claimed one.

#### D2. The review queue contains 100% hallucinated records

- 3 records (generic `Sr`, `Lr`, `Yr` → varieties HD2781, HD3086, GW322, NW1014) come from PMID 37228583. That is a neural stem cell paper. The varieties were copied from the made-up NOTE.
- 1 record (Yr81) comes from PMID 33153977. That is a 1-page sports medicine editorial.
- Also note that "Sr", "Lr", "Yr" are gene *families* (prefixes), not genes. The validator accepted them.

#### D3. The seed data (`curator/seed_data.py`) contains factual errors

Check every row against the *Catalogue of Gene Symbols for Wheat*, SoyBase, and the primary papers before reusing anything.

| Seed claim | Problem | Correct / action |
|---|---|---|
| Sr33 on 1B, "APR", carried by Chinese Spring | Sr33 is on **1DS** (from *Ae. tauschii*; Periyannan et al. 2013, *Science*, PMID 23811228). It is an all-stage NLR, and Chinese Spring does not carry it. | Fix chromosome, type and variety — verified and loaded correctly in `kg/curated/wheat_seed_genes.yaml` |
| Sr35 on "9B" | **Wheat has no chromosome 9.** Sr35 is on **3AL** (from *T. monococcum*). | Fix |
| Sr36 on 2D | Sr36 is on **2BS** (from *T. timopheevii*) | Fix |
| Sr39 on 7B, "APR" | On **2B** (*Ae. speltoides* translocation), all-stage | Fix |
| Lr18 on 7D | **5BL** (from *T. timopheevii*) | Fix |
| Lr21 on 5D | **1DS** | Fix |
| Yr21 on 2B | **1B** | Fix |
| Yr18 as its own gene | Same gene as **Lr34/Yr18/Sr57/Pm38** (7DS). This creates duplicate entities. | Model as synonyms |
| Ml26 (powdery mildew) | Not a wheat Pm gene symbol. The *Ml-* prefix is barley mildew nomenclature. | Remove |
| All wheat genes "carried by Chinese Spring" | Chinese Spring is the classic **susceptible** reference. It lacks the alien-derived Sr33/35/36/39 and Lr21/24. It *does* carry Lr34/Yr18. | Rebuild CARRIES from evidence |
| Scn3 (soybean SCN) | Not a standard locus. SCN resistance loci are **rhg1 (Gm18)** and **Rhg4 (Gm08)**. | Replace |
| Rps6 on chromosome 3 | Rps6 is on **Gm18** | Fix |
| Rst (SDS) | Not a recognized locus. SDS resistance is reported as *Rfs*/qRfs QTLs. | Remove/replace |
| Cre8 → soybean cyst nematode | **Cre8 is a wheat cereal cyst nematode (*H. avenae*) gene on 6BL** | Remove from soybean |
| Williams 82 carries Rps1a, Rps6, Scn3… | Williams 82 carries **Rps1k** and is SCN-**susceptible** | Fix |
| Ca_LG3_10250, Ca_LG1_5420… | **Made-up IDs.** Real ICC4958 gnm2 IDs look like `Ca_00001`. Chickpea resistance is mostly QTL/loci (e.g., the *foc1–foc5* wilt cluster on CaLG2; ascochyta QTLs on CaLG3/CaLG4). | Replace with literature loci |
| "Use resistant rootstock" (chickpea wilt) | Chickpea is not grafted | Use official package-of-practice advice |
| `source: "IWGSC RefSeq v2.1"` for resistance claims | A genome assembly is not evidence for a resistance claim | Cite the primary paper (PMID/DOI) |
| `confidence: "Very High"` | Invented. Confidence must be *computed from evidence* (Section 4.4). | Remove |

**Rule going forward:** no hand-typed or LLM-typed fact enters the KG without a citation plus a verbatim evidence quote that has been checked against the source text.

#### D4. The genome datasets are used only for counts

`run_pipeline.process_dataset()` parses all genes and then only writes `genome_gene_count` to the Crop node. `load_genes.py` is never called. The GFFs contain far more value:

| File | Genes | Useful annotation present | R-gene candidates found (quick scan) |
|---|---|---|---|
| Wheat RefSeq v2.1 GFF (810 MB) | 136,408 gene features (103,799 protein-coding) | `description=` product names | **1,737** genes described as "disease resistance…" (RGA, RPM1, Pik-2, Lr10-like…) |
| Soybean Wm82 gnm6 GFF3 (180 MB) | 48,387 | Gene3D/Prosite/Superfamily Dbxrefs, `Note=` product, `ancestorIdentifier` (a4 IDs) | **374** NB-ARC (IPR002182/PF00931) |
| Chickpea ICC4958 gnm2 GFF3 (74 MB) | 30,257 | InterPro, PANTHER, Superfamily Dbxrefs, `Note=` | **121** NB-ARC |
| Chickpea GBFF (752 MB) | **0** gene features | none | Remove it from the pipeline |

**The key limitation to understand:** a reference genome describes *one* cultivar (Chinese Spring, Williams 82, ICC4958). It cannot tell you which *variety* is susceptible. Variety-level knowledge has to come from (a) phenotyping trials, (b) marker/haplotype genotyping of varieties, (c) pedigree and gene postulation, and (d) literature. The reference genomes serve as the **coordinate system** for linking QTLs, markers and candidate genes.

#### D5. The data needed for the actual objective is missing

- **No susceptibility or reaction data.** You need variety reaction scores from multi-location screening trials (see Section 5).
- **No environmental trigger data.** The current `iot_trigger` strings (`"high_humidity"`) are not usable by a sensor rule engine. You need numeric envelopes with durations and growth stages.
- **No pathotype/race data.** Resistance is race-specific: Sr31 was defeated by Ug99, and Yr9/Lr26 were defeated in India. Without pathotypes, "resistant" is misleading.
- **No India-specific authoritative sources**, such as AICRP trial reports from ICAR-IIWBR Karnal (wheat), **ICAR-IISR Indore (soybean, in the same city as IIT Indore)** and ICAR-IIPR Kanpur (chickpea), or notified-variety lists.

#### D6. Coordinate-version mismatch (not yet noticed)

QTL positions in papers use different assemblies: CS RefSeq v1.0 vs v2.1, Wm82.a1/a2/a4 vs gnm6, and CDC Frontier vs ICC4958 for chickpea. You cannot copy coordinates from a paper directly onto v2.1/gnm6 genes. You must **anchor through marker sequences** (BLAST or minimap2 of the flanking-marker primer/probe sequences against your reference) or through official liftover tables.

### 2.3 Technique problems

#### T1. LLM extraction method

| Issue | Where | Effect |
|---|---|---|
| Whole paper sent in one call (up to 193 KB), no chunking or section filter | `paper_extractor.py` | Exceeds free-tier token limits, and the model attends to noise |
| Made-up header sent with the text | `fetch_papers.py` writes TITLE/NOTE | Direct source of hallucinations |
| No evidence quote, no grounding check | extractor | Hallucinations cannot be detected |
| LLM asked to self-report "confidence" | prompt | Meaningless numbers presented as facts |
| Free-text entities, no normalization | extractor/loader | "Yellow Rust" vs "Stripe Rust" become separate diseases, and "Sr" becomes a gene |
| Tables ignored (text flattened from XML) | fetcher | Variety reaction tables, the most valuable data, are lost |
| JSON parsed from free text; no schema-constrained output | extractor | Fragile |
| Provider confusion: docs say Gemini, code uses Groq, error messages say Gemini, `google-generativeai` is an unused dependency | several | Unreproducible |
| Model and prompt versions not recorded per record | extractor | Not reproducible or auditable |

#### T2. Schema

- Missing entities: Pathogen, Pathotype/Race, QTL, Marker, EnvironmentalTrigger, GrowthStage, AgroZone/Location, Publication, Evidence/Claim, Trial.
- `Gene.id` is not namespaced by crop and has no synonym handling (Lr34 = Yr18 = Sr57 = Pm38; Lr67 = Yr46 = Sr55 = Pm46).
- `Treatment` hangs off `Disease` and ignores context (variety, stage, zone). Chemical advice needs an authoritative source such as an ICAR Package of Practices or the CIB&RC label claims.
- `CARRIES {confidence}` is part of the MERGE key, so different confidence values create duplicate edges.
- `seed_loader` MERGEs `CONFERS_RESISTANCE_TO {confidence, source}`, while `loader._EDGE_QUERY` MERGEs without properties and **overwrites `source`**. Multi-source provenance is lost, and the two loaders behave inconsistently.

#### T3. Pipeline and code bugs

| # | Bug | File |

## 3. Target architecture

```
                        ┌──────────────────────── SOURCES (verified) ───────────────────────┐
                        │ Literature: Europe PMC / NCBI E-utils (OA, JATS XML, license)     │
                        │ Catalogues: Wheat gene symbols, SoyBase, LIS, GrainGenes, PRGdb   │
                        │ Trials: AICRP reports (IIWBR, IISR, IIPR), GRIN-Global evals,     │
                        │         ICRISAT mini-core, published supplementary tables         │
                        │ Genomes: RefSeq v2.1 / gnm6 / ICC4958 GFF3 (+ protein FASTA)      │
                        │ Genotypes: SoySNP50K, wheat SNP-array panels, chickpea 3K-RG      │
                        │ Weather: NASA POWER / IMD gridded (validation of triggers)        │
                        └───────────────┬───────────────────────────────────────────────────┘
                                        │ ingest + checksum + license + metadata verification
                                        ▼
  data/raw/ (gitignored) ──► data/interim/ (parsed sections, tables, gene tables; Parquet)
                                        │
             ┌──────────────────────────┼──────────────────────────────────┐
             ▼                          ▼                                  ▼
   Structured parsers          LLM extraction (grounded)          Genomic computation
   (tables, catalogues,        chunk → NER prefilter → JSON-      (NLR candidates, QTL→
    trial reports)             schema output → quote check)       gene intervals, markers)
             └──────────────────────────┼──────────────────────────────────┘
                                        ▼
                         Normalization (ontology IDs, synonyms)
                                        ▼
                   Human review (prioritized by uncertainty; audited)
                                        ▼
     ╔══════════════ CANONICAL KG STORE (versioned, in git / Zenodo) ═════════════╗
     ║ kg/nodes/*.tsv  kg/claims.tsv  kg/evidence.tsv  kg/publications.tsv        ║
     ║ + confidence scores computed by code, + build manifest (hashes, versions)  ║
     ╚═════════════════════════════════════╤══════════════════════════════════════╝
                                           │ `agrihub kg build` (deterministic, < 20 min)
                   ┌───────────────────────┼─────────────────────────┐
                   ▼                       ▼                         ▼
          PostgreSQL + PostGIS       DuckDB/Parquet             Release bundle
          (Supabase; schema/release)  (analytics, ML)            (Zenodo DOI, KGX TSV)
                   │
                   ▼
   FastAPI /v1 on Cloud Run (Cloudflare in front): /search /varieties /risk /features /claims /stats
                   │
      ┌────────────┼──────────────┬──────────────────┐
      ▼            ▼              ▼                  ▼
   Web UI     IoT risk engine   Phenomic model     Yield model
```

**Principles**

1. **The graph is disposable. The canonical files are the truth.** If the database is lost, `agrihub kg build && agrihub kg load` restores it in minutes.
2. **Every fact is a Claim backed by at least one Evidence record** (source, locator, quote, method, extractor version, reviewer).
3. **Confidence is computed, never typed.**
4. **Structured sources first, LLM second.** Use the LLM only where no structured source exists, and always with grounding.
5. **Everything is versioned:** dataset checksums, prompt versions, model IDs, ontology versions, KG release tags.

**Recommended stack (free):** Python 3.12, `pydantic` v2 (schemas), `httpx` + `tenacity` (HTTP/retry), `lxml` (JATS XML), `duckdb` + `pyarrow` (staging), `rapidfuzz` (grounding), `typer` (CLI), `psycopg` + `fastapi` (serving), `pronto` (ontologies), `pytest`. Supabase (Postgres + PostGIS) for staging/production, a throwaway local Postgres for tests. Full reasoning is in TECH_STACK.md. Keep the LLM provider behind one interface (`curator/llm/client.py`) so it can be swapped. Pin model IDs and log them per record.

## 4. Knowledge model (schema v2)

### 4.1 Nodes

| Label | Key (namespaced ID) | Important properties | Ontology / authority |
|---|---|---|---|
| `Crop` | `crop:wheat` | name, species, NCBITaxon | NCBITaxon:4565 (wheat), 3847 (soybean), 3827 (chickpea) |

| `RefGene` | `ref:wheat:LOC123…` | locus_id, chromosome, start, end, strand, description, domains[] (InterPro), is_nlr | From your GFF3 files |
| `Disease` | `dis:wheat:stripe_rust` | name, synonyms (yellow rust), crop, Crop-Ontology trait ID | CO_321 / CO_336 / CO_338 |

| `EnvTrigger` | `env:dis:wheat:stripe_rust:infection` | variable (air_temp, rh, leaf_wetness_h, soil_moisture, soil_temp, rainfall), min, max, unit, duration_h, aggregation, stage window | PECO, BBCH/Zadoks |
| `GrowthStage` | `gs:BBCH:61` | code, name, crop-specific mapping | BBCH / Zadoks |

| `Advisory` | `adv:…` | action, type (cultural/biological/chemical), authority (PoP document) | ICAR Package of Practices |

### 4.2 Relationships (shortcut edges, materialised from Claims for fast queries)

```
(Variety)-[:BELONGS_TO]->(Crop)
(Variety)-[:RECOMMENDED_FOR {season}]->(AgroZone)
(Variety)-[:HAS_REACTION {reaction: R|MR|MS|S|HS, score, scale, stage: seedling|adult,
                          pathotype, n_locations, seasons, tier, score_num}]->(Disease)      ← core edge
(Variety)-[:CARRIES {method: marker|postulation|pedigree|sequence|haplotype, tier}]->(Gene)
(Variety)-[:DERIVED_FROM]->(Variety)                                                  (pedigree)
(Gene)-[:CONFERS_RESISTANCE_TO {type: ASR|APR, spectrum, tier}]->(Disease)
(Gene)-[:EFFECTIVE_AGAINST {tier}]->(Pathotype)
(Gene)-[:DEFEATED_BY {first_year, region, tier}]->(Pathotype)
(Gene)-[:SAME_AS]->(Gene)                                   (Lr34≡Yr18≡Sr57≡Pm38 via synonyms)
(Gene)-[:LOCATED_AT]->(RefGene)                             (cloned gene ↔ reference locus)
(QTL)-[:ASSOCIATED_WITH]->(Disease)
(QTL)-[:CONTAINS]->(RefGene)                                (positional candidates; is_nlr flag)
(Marker)-[:LINKED_TO {distance_cM, diagnostic}]->(Gene|QTL)
(Disease)-[:CAUSED_BY]->(Pathogen)
(Pathotype)-[:VARIANT_OF]->(Pathogen)
(Pathotype)-[:PREVALENT_IN {years}]->(AgroZone)
(Disease)-[:FAVOURED_BY {phase: infection|sporulation|spread}]->(EnvTrigger)
(EnvTrigger)-[:DURING]->(GrowthStage)
(Disease)-[:MANAGED_BY]->(Advisory)
(Claim)-[:SUBJECT]->(any)   (Claim)-[:OBJECT]->(any)   (Claim)-[:SUPPORTED_BY]->(Evidence)
(Evidence)-[:FROM]->(Publication|Dataset|Trial)
```

Every fact is stored as a `Claim` row (full provenance; in Postgres the `claim` + `evidence` tables, see TECH_STACK.md §5), and the builder **materialises** the shortcut relation (for example `HAS_REACTION`) with `claim_ids[]`, `tier` and `confidence_score` for fast API queries.

### 4.3 Claim types (the contract between extractors and the store)

| Claim type | Subject → Object | Required qualifiers |
|---|---|---|
| `VARIETY_REACTION` | Variety → Disease | reaction, stage, (location, season, pathotype, scale) |
| `VARIETY_CARRIES_GENE` | Variety → Gene | method |
| `GENE_CONFERS_RESISTANCE` | Gene → Disease | resistance type (ASR/APR), (spectrum) |
| `GENE_PATHOTYPE_INTERACTION` | Gene → Pathotype | effective/defeated, (year, region) |
| `QTL_ASSOCIATION` | QTL → Disease | chromosome, markers/interval, LOD or p, PVE |
| `MARKER_LINKAGE` | Marker → Gene/QTL | distance or diagnostic |
| `DISEASE_ENV_TRIGGER` | Disease → EnvTrigger | variable, range, unit, duration, stage |
| `PATHOTYPE_PREVALENCE` | Pathotype → AgroZone | years |

### 4.4 Computed confidence (replaces the invented "Very High/High/Medium")

Each Evidence record gets a weight `w` from **evidence type** (mapped to ECO codes):

| Evidence type | w |
|---|---|
| Gene cloned + functionally validated (transgenic complementation, mutants) | 1.00 |
| Diagnostic marker genotyping / sequence-confirmed haplotype | 0.85 |
| Multi-location field screening (≥ 3 locations or seasons), standard scale | 0.80 |
| Fine-mapping / bi-parental QTL (LOD ≥ 3, replicated) | 0.70 |
| GWAS association (significant after multiple-testing correction) | 0.60 |
| Single-location or greenhouse screening | 0.50 |
| Gene postulation / pedigree inference | 0.45 |
| Review article statement (resolve to the primary paper when possible) | 0.35 |

Modifiers: `× 0.6` if extracted by LLM and not yet human-reviewed; `× 0.8` if the pathotype-dependent evidence is more than 10 years old.
Aggregate: `score = 1 − Π(1 − w_i)` over independent sources (different publications/trials). Conflicting evidence (R vs S for the same pair and stage) sets `conflict=true` and caps the tier at C.
Tiers: **A** ≥ 0.85 · **B** ≥ 0.65 · **C** ≥ 0.40 · **D** < 0.40. The API returns the tier and the claim IDs so the UI can show "why".

*(These weights are a documented, tunable heuristic. In the paper, present them as such and run a sensitivity analysis.)*

### 5.4 Tier 3: genomic computation (your datasets)

1. **R-gene candidate catalogue:** from the GFF annotations (and InterProScan on proteins where Dbxrefs are missing), flag NB-ARC (IPR002182), TIR (IPR000157), LRR (IPR001611/IPR032675), RPW8 (IPR008808), CC, and kinase domains. Classify as TNL/CNL/RNL/RLK/RLP. Compare with PRGdb/DRAGO.

## 6. Extraction methodology (LLM done right)

```
Paper (verified PMID/PMCID, OA license)
  → JATS XML → sections {abstract, methods, results, discussion} + tables (structured rows)
  → Relevance classifier (keywords + NER counts; drop if crop/disease terms absent)
  → Dictionary NER: gene regexes (Sr\d+[a-z]?, Lr\d+, Yr\d+, Pm\d+, Rps\d+[a-z]?, Rpp\d+, Rhg\d, foc\d …),
                   variety lexicon (notified lists + synonyms), pathogen taxa, pathotype patterns
  → Select chunks containing ≥1 entity pair (gene/variety + disease/pathotype)  ← cuts tokens by ~80–90%
  → LLM call per chunk: JSON-schema-constrained output, typed claims, temperature 0,
                        MUST include verbatim `evidence_quote` and `section`
  → Grounding check: fuzzy-match quote in chunk (rapidfuzz partial_ratio ≥ 92) AND both entities in quote
  → Normalization: map strings → canonical IDs; unknown → `needs_review`
  → Review UI (priority = low grounding score, new entity, conflict) → decision logged
  → Claim + Evidence rows appended to canonical store
```

**Example claim output (schema-validated with pydantic):**

```json
{
  "claim_type": "VARIETY_REACTION",
  "subject": {"type": "Variety", "text": "HD 3086", "normalized_id": "var:wheat:HD3086"},
  "object":  {"type": "Disease", "text": "leaf rust", "normalized_id": "dis:wheat:leaf_rust"},
  "qualifiers": {"reaction": "S", "stage": "adult", "pathotype": "77-5", "location": "Karnal", "season": "2019-20"},
  "evidence": {
    "source_id": "pmid:XXXXXXXX", "section": "results", "table_id": null,
    "quote": "HD3086 showed susceptible reaction (60S) to pathotype 77-5 at Karnal",
    "method": "ECO:0007034",
    "extractor": "llm:<model-id>@prompt-v3"
  }
}
```

**Rules**
- Never send the fetcher's own header to the LLM. Store metadata separately.
- Gene families ("Sr genes", "Lr genes") are not genes. Reject them unless a number or allele is present.
- Review articles: extract the claim, then try to resolve the cited primary paper and link it. Give the review lower weight.
- Store the prompt text in `curator/llm/prompts/<name>_v<N>.md`. The version goes into every Evidence record.

### 6.1 Evaluation (the part that makes it research-grade)

- **Gold standard:** about 45 papers (15 per crop, stratified: primary QTL/GWAS, variety screening, reviews), annotated independently by 2 people using the same claim schema. Report **inter-annotator agreement** (Cohen's κ for claim-level agreement), then adjudicate.
- **Metrics:** entity P/R/F1, claim P/R/F1 (strict = all qualifiers match; relaxed = subject+object+polarity), **grounding rate**, **hallucination rate** (claims whose quote is absent or doesn't support the claim), normalization accuracy.
- **Ablations:** (a) full paper vs NER-selected chunks, (b) with vs without the JSON schema, (c) with vs without the grounding filter, (d) 2–3 different LLMs (at least one open-weight model for reproducibility), (e) tables by parser vs by LLM.
- **Targets:** claim precision ≥ 0.90 after grounding, recall ≥ 0.70, hallucination ≤ 2%.
- **KG-level evaluation:** coverage vs reference catalogues (% of catalogued wheat Sr/Lr/Yr genes with a chromosome and at least one disease claim), CQ answerability (all 12 CQs return correct answers on a hand-built test set), and consistency checks (constraint violations = 0).

### 7.3 Risk engine (`POST /api/risk`)

```
risk(disease) = env_match(sensor_window, EnvTrigger, stage)            ∈ [0,1]
              × susceptibility(variety, disease, zone)                  ∈ [0,1]  (S=1, MS=0.7, MR=0.35, R=0.1, unknown=0.6)
              × inoculum_prior(disease, zone, season)                   ∈ [0,1]  (pathotype prevalence, history)
flag = risk ≥ θ_disease (θ tuned by back-testing on historical epidemics)
```

The response contains the flags, a risk score, which conditions matched, the variety reaction plus its evidence tier, pathotype notes, and the authoritative advisory. **The IoT team needs this explanation for every flag.**

## 11. Risks and mitigations

| Risk | Mitigation |
|---|---|
| LLM hallucination re-enters | Grounding check is mandatory; no quote means no claim; the gold-set metric is tracked per release |
| AICRP data only available as PDFs, or restricted | Formal request via ICAR institutes (IISR Indore is local); cite reports; fall back to published papers and GRIN |
| Assembly-version mismatch corrupts coordinates | Anchor via marker sequences; store assembly version on every coordinate |
| Hosting deletion or free-tier changes | Canonical files + one-command rebuild; nightly pg_dump to R2; local PostGIS for development |
| Scope creep (22 languages, multi-country…) | Frozen scope doc; everything else goes to "post-v1" |
| Env-trigger values vary by source | Store ranges per source; use a consensus envelope with a spread; back-test chooses |
| Susceptibility changes as pathotypes evolve | Reaction claims carry season, pathotype and recency decay; annual refresh |
| Legal/licensing of text mining | Only OA-licensed full text; store quotes ≤ 1–2 sentences with the citation |

## Appendix A: Example Cypher for key CQs (schema v2)

> These describe the graph semantics. In production they are implemented as SQL over `claim`/`entity` (TECH_STACK.md §5). The same queries can run on the optional Neo4j export bundle.

```cypher
// CQ1: susceptible notified varieties in a zone for a disease
MATCH (v:Variety)-[:RECOMMENDED_FOR]->(:AgroZone {id: $zone}),
      (v)-[r:HAS_REACTION]->(d:Disease {id: $disease})
WHERE r.reaction IN ['S','MS','HS'] AND r.tier IN ['A','B']
RETURN v.name, r.reaction, r.stage, r.pathotype, r.tier, r.claim_ids
ORDER BY r.score_num DESC;

// CQ3: genes carried by a variety and their status vs pathotypes prevalent in its zones (last 5 yrs)
MATCH (v:Variety {id: $variety})-[c:CARRIES]->(g:Gene)
OPTIONAL MATCH (g)-[x:DEFEATED_BY]->(p:Pathotype)-[pr:PREVALENT_IN]->(z:AgroZone)<-[:RECOMMENDED_FOR]-(v)
WHERE any(y IN pr.years WHERE y >= date().year - 5)
RETURN g.symbol, c.method, c.tier, collect(DISTINCT p.designation) AS defeated_by_prevalent;

// CQ5: QTLs for a disease and NLR candidates in the interval
MATCH (q:QTL)-[:ASSOCIATED_WITH]->(:Disease {id: $disease})
OPTIONAL MATCH (q)-[:CONTAINS]->(rg:RefGene {is_nlr: true})
RETURN q.id, q.chromosome, q.lod, q.pve, collect(rg.locus_id) AS nlr_candidates;

// CQ10: conflicting reactions
MATCH (v:Variety)-[r1:HAS_REACTION]->(d:Disease)<-[r2:HAS_REACTION]-(v)
WHERE id(r1) < id(r2) AND r1.stage = r2.stage
  AND ((r1.reaction IN ['R','MR'] AND r2.reaction IN ['S','MS','HS'])
    OR (r2.reaction IN ['R','MR'] AND r1.reaction IN ['S','MS','HS']))
RETURN v.name, d.name, r1.reaction, r2.reaction, r1.claim_ids + r2.claim_ids;
```
