# Supabase project files

Local scaffold created by the Supabase CLI (`supabase init`), plus this project's own
migrations. **No project is linked from this machine/session** — nothing here has touched
your actual Supabase project. You run everything by hand, per TECH_STACK.md ADR-2.

| Path | What it's for |
|---|---|
| `config.toml` | Local dev config (`supabase start`), generated by the CLI. Not project-specific until linked. |
| `migrations/` | Versioned SQL for the **fixed** app schema: extensions, and later the `ops`/`public` tables (Phase 2) and any `pg_cron` jobs (Phase 8+). Numbered by timestamp, applied in order. |
| `functions/` | Edge Functions — empty for now, see `functions/README.md` for when to use one. |

**What does *not* live here:** the KG release schemas (`kg_<release>`, e.g. `kg_2026_10_1`).
Those are created and loaded by the Python pipeline (`curator/graph/pg.py`, using
`db/release_schema.sql`) at build time, not by a fixed migration — a new release is a new
schema, not a change to an existing one. See RESEARCH_ROADMAP.md §2.3 (ADR-7).

## Your workflow right now: paste into the Supabase SQL Editor

You're running migrations manually rather than via `supabase db push`, which is fine — the
files are the same either way; only how they get executed differs. For each new file in
`migrations/`, open it, copy its contents, paste into the project's SQL Editor, and run it
**once**, in filename order (the timestamp prefix is the order).

### After this change, run in your Supabase project (in this order)

1. **`migrations/20260925081644_enable_extensions.sql`** — turns on `pg_trgm` (fuzzy search)
   and `postgis` (zone maps), and grants the built-in roles usage on the `extensions` schema.
   This is the fix for the `gin_trgm_ops does not exist` error: that error means pg_trgm
   isn't enabled yet. Safe to re-run; every statement is idempotent.
2. Re-run (or run for the first time) **`db/release_schema.sql`** — it's fixed too, and now
   works standalone: create a schema, `SET search_path` to it (or not — the trigram index and
   the ops it needs are schema-qualified now), then paste the file. Example:
   ```sql
   CREATE SCHEMA kg_dev;
   SET search_path = kg_dev;
   -- paste db/release_schema.sql here
   ```
3. Optional, only if you want to test the zone-map tables now: same schema,
   **`db/release_schema_postgis.sql`** after step 2.

Nothing else needs turning on for Phase 1. `pg_cron` is deliberately **not** enabled yet
(see the comment at the top of the extensions migration) — turn it on via
**Dashboard → Database → Extensions** when Phase 8 needs it, since the SQL-only path can hit
a permissions error for that particular extension.

## When you're ready to link and automate (later, not now)

```bash
supabase login
supabase link --project-ref <your-staging-project-ref>
supabase db push          # applies every migration in order, tracked in a history table
```

From then on, `db push` replaces the copy-paste step for files in `migrations/` (the release
schemas built by the Python pipeline are unaffected either way).
